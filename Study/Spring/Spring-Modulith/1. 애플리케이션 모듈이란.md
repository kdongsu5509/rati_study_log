## 애플리케이션 모듈 (Application Modules)
- `Module`
	- 특정 역할(도메인)을 수행하는 패키지(디렉토리)

애플리케이션 모듈의 구성요소는 다음과 같아요.

- `Provided Interface`  : 내가 남에게 **주는** 기능
	- 다른 모듈에 노출되는 API : 외부에서 호출할 수 있는 `public` 서비스 클래스나 인터페이스 (예: `OrderService`).
	- 애플리케이션 이벤트 : 외부에 던지는 알림 

- `Internal Component` : 모듈 내에서만 사용하는 요소들
	- 외부 모듈이 직접 호출하면 안 되는 비즈니스 로직, 데이터베이스 처리 클래스 등

- `Required Interface` : 내가 남에게 **받아야 하는** 기능
	- Spring 빈 의존성: 다른 모듈의 서비스를 주입받아 쓰는 것 (예: `OrderModule`이 결제를 위해 `PaymentService`를 의존하는 것).
	- 리스닝하는 이벤트: 다른 모듈이 발행한 알림을 듣는 것 (예: "결제 완료" 이벤트를 구독)
	- 노출된 설정 프로퍼티 : 외부(`application.properties` 등)에서 주입받는 모듈 설정값.

### ApplicationModules
- `ApplicationModules` 는 어떤 모듈들이 있고, 각 [[1. 애플리케이션 모듈이란#애플리케이션 모듈 (Application Modules)|애플리케이션 모듈 구성요소]]가 어떻게 짜여있는지" 확인하고 검사하는 핵심 클래스에요.
	- `@SpringBootApplication`이 있는 곳을 기준으로 아래 디렉토리(패키지) 들을 분석해요
	- 이후 메모리 상에 패키지가 어떤 모듈을 나타내는지 소유하는 모듈 지도를 만들어요.

**인스턴스 생성**
```java
var modules = ApplicationModules.of(Application.class);
```
- `var modules` 는 메모리에 애플리케이션 모듈 배치(일종의 지도)을 가지고 있어요. 이 중 어떤 부분이 모듈로 감지될 지는 패키지의 구조 혹은 설정에 따라 달라져요. 이 부분에 대해서는 다른 곳에서 다루고 있어요.
	- 모듈 배치는 다음과 같이 확인할 수 있어요
```java
modules.forEach(System.out::println);
```
```plainText
## example.inventory ##
> Logical name: inventory
> Base package: example.inventory
> Spring beans:
  + ….InventoryManagement
  o ….SomeInternalComponent

## example.order ##
> Logical name: order
> Base package: example.order
> Spring beans:
  + ….OrderManagement
  + ….internal.SomeInternalComponent
```

### 아키텍처 검증
[[1. 애플리케이션 모듈이란#ApplicationModules|ApplicationModules]] 는 검증에서도 사용되요.

```java
var modules = ApplicationModules.of(Application.class);
modules.verify();
```

애플리케이션 모듈 검사에서 특정 Java 클래스나 전체 패키지를 제외하고 싶다면 다음과 같이 할 수도 있어요.

```java
ApplicationModules.of(
	Application.class, 
	JavaClass.Predicates.resideInAPackage("com.example.db")
).verify();
```

```kotlin
ApplicationModules.of(
	Application::class.java, 
	JavaClass.Predicates.resideInAPackage("com.example.db")
).verify()
```

제외 문자열은 다음과 같이 설정할 수 있어요.
* `com.example.db` 
	*  지정된 패키지 `com.example.db`에 있는 모든 파일 제외
* `com.example.db..` 
	* 지정된 패키지(`com.example.db`)
	* 모든 하위 패키지(`com.example.db.a` 또는 `com.example.db.b.c`)에 있는 모든 파일
* `..example..` 
	* `a.example`, `a.example.b`, `a.b.example.c.d`의 경우에는 일치 -> 제외 대상
	* `a.exam.b` -> 제외 대상 아님.

나머지 `matcher` 에 대한 자세한 내용은 JavaDoc of ArchUnit [`PackageMatcher`](https://github.com/TNG/ArchUnit/blob/main/archunit/src/main/java/com/tngtech/archunit/core/domain/PackageMatcher.java). 에서 찾을 수 있어요.


### 단순한 애플리케이션 모듈 (Simple Application Modules)

애플리케이션의 메인 패키지는 메인 애플리케이션 클래스가 위치한 패키지입니다. 이는 `@SpringBootApplication` 어노테이션이 붙어 있고 보통 이를 실행하는 데 사용되는 `main(…)` 메서드를 포함하는 클래스입니다. 기본적으로 메인 패키지의 각 직속 하위 패키지는 하나의 애플리케이션 모듈 패키지로 간주됩니다.

이 패키지가 하위 패키지를 포함하지 않는다면, 이는 단순한(simple) 모듈로 간주됩니다. 이는 Java의 패키지 스코프(package scope)를 사용하여 다른 패키지에 있는 코드가 해당 타입을 참조하지 못하도록 코드 내부를 숨길 수 있게 해주며, 결과적으로 해당 패키지들로의 의존성 주입 대상에서 제외됩니다. 따라서 자연스럽게 모듈의 API는 패키지 내의 모든 `public` 타입으로 구성됩니다.

예시 배치 구조를 살펴보겠습니다 (`+`는 `public` 타입을, `o`는 package-private 타입을 나타냅니다).

**단일 inventory 애플리케이션 모듈**

```text
 Example
╰─  src/main/java
   ├─  example                        
   │  ╰─  Application.java
   ╰─  example.inventory              
      ├─  InventoryManagement.java
      ╰─  SomethingInventoryInternal.java

```

애플리케이션의 메인 패키지는 `example`입니다. 애플리케이션 모듈 패키지는 `inventory`입니다.

### 고급 애플리케이션 모듈 (Advanced Application Modules)

만약 애플리케이션 모듈 패키지가 하위 패키지들을 포함하고 있다면, 바로 그 동일한 모듈의 코드에서 참조할 수 있도록 해당 하위 패키지 안의 타입들을 `public`으로 만들어야 할 수도 있습니다.

**inventory 및 order 애플리케이션 모듈**

```text
 Example
╰─  src/main/java
   ├─  example
   │  ╰─  Application.java
   ├─  example.inventory
   │  ├─  InventoryManagement.java
   │  ╰─  SomethingInventoryInternal.java
   ├─  example.order
   │  ╰─  OrderManagement.java
   ╰─  example.order.internal
      ╰─  SomethingOrderInternal.java

```

이러한 배치에서 `order` 패키지는 API 패키지로 간주됩니다. 다른 애플리케이션 모듈의 코드가 이 패키지 내부의 타입을 참조하는 것이 허용됩니다. `order.internal`은 애플리케이션 모듈 베이스 패키지의 다른 모든 하위 패키지와 마찬가지로 내부(internal) 패키지로 간주됩니다. 이 내부 패키지 안의 코드는 다른 모듈에서 참조해서는 안 됩니다.

여기서 `SomethingOrderInternal`이 `public` 타입이라는 점에 주목하세요. 아마도 `OrderManagement`가 이에 의존하기 때문일 것입니다. 불행하게도 이는 이 타입이 `inventory`와 같은 다른 패키지에서도 참조될 수 있음을 의미합니다. 이 경우 Java 컴파일러는 이러한 잘못된 참조를 방지하는 데 큰 도움이 되지 않습니다.

### 중첩된 애플리케이션 모듈 (Nested Application Modules)

1.3 버전부터 Spring Modulith 애플리케이션 모듈은 중첩된 모듈(nested modules)을 포함할 수 있습니다. 이를 통해 하나의 모듈이 다시 논리적으로 분리되어야 하는 부분들을 포함하고 있는 경우 내부 구조를 제어할 수 있습니다. 중첩된 애플리케이션 모듈을 정의하려면, 모듈을 구성하려는 패키지에 `@ApplicationModule` 어노테이션을 명시적으로 붙이면 됩니다.

```text
 Example
╰─  src/main/java
   │
   ├─  example
   │  ╰─  Application.java
   │
   │  -> Inventory
   │
   ├─  example.inventory
   │  ├─  InventoryManagement.java
   │  ╰─  SomethingInventoryInternal.java
   ├─  example.inventory.internal
   │  ╰─  SomethingInventoryInternal.java
   │
   │  -> Inventory > Nested
   │
   ├─  example.inventory.nested
   │  ├─  package-info.java // @ApplicationModule
   │  ╰─  NestedApi.java
   ├─  example.inventory.nested.internal
   │  ╰─  NestedInternal.java
   │
   │  -> Order
   │
   ╰─  example.order
      ├─  OrderManagement.java
      ╰─  SomethingOrderInternal.java

```

이 예시에서 `inventory`는 위에서 설명한 바와 같은 애플리케이션 모듈입니다. 중첩된 패키지에 있는 `@ApplicationModule` 어노테이션으로 인해 해당 패키지가 다시 중첩된 애플리케이션 모듈이 되었습니다. 이러한 배치에서는 다음과 같은 접근 규칙이 적용됩니다:

* `Nested` 안의 코드는 `Inventory` 또는 `Inventory` 내부에 중첩된 형제(sibling) 애플리케이션 모듈들이 노출한 타입에서만 사용할 수 있습니다.
* `Nested` 모듈 안의 모든 코드는 부모 모듈의 코드에 접근할 수 있으며, 이는 내부(internal) 패키지인 경우에도 마찬가지입니다. 즉, `NestedApi`와 `NestedInternal` 모두 `inventory.internal.SomethingInventoryInternal`에 접근할 수 있습니다.
* 중첩된 모듈의 코드는 최상위(top-level) 애플리케이션 모듈이 노출한 타입에도 접근할 수 있습니다. `nested`(또는 임의의 하위 패키지) 안의 모든 코드는 `OrderManagement`에 접근할 수 있습니다.

### 열린 애플리케이션 모듈 (Open Application Modules)

앞서 설명한 배치는 노출하기로 능동적으로 선택된 타입만 다른 모듈에 노출하므로 닫힌(closed) 모듈로 간주됩니다. Spring Modulith를 레거시 애플리케이션에 적용할 때, 중첩된 패키지에 위치한 모든 타입을 다른 모듈로부터 숨기는 것은 부적절하거나, 해당 패키지들을 모두 노출 대상으로 표시해야 하는 번거로움이 있을 수 있습니다.

애플리케이션 모듈을 열린(open) 모듈로 전환하려면, `package-info.java` 타입에 `@ApplicationModule` 어노테이션을 사용하세요.

**애플리케이션 모듈을 열린 모듈로 선언하기**

* **Java** / **Kotlin**
```java
@org.springframework.modulith.ApplicationModule(
  type = Type.OPEN
)package example.inventory;

```



애플리케이션 모듈을 열린 모듈로 선언하면 검증(verification)에 다음과 같은 변화가 생깁니다:

* 다른 모듈에서 애플리케이션 모듈의 내부(internal) 타입에 접근하는 것이 일반적으로 허용됩니다.
* 애플리케이션 모듈 베이스 패키지의 하위 패키지에 존재하는 타입을 포함한 모든 타입이, 이름 없는 명명된 인터페이스(unnamed named interface)에 추가됩니다. 단, 이름 있는 인터페이스(named interface)에 명시적으로 할당된 경우는 제외됩니다.

> 이 기능은 기존 프로젝트의 코드베이스를 Spring Modulith가 권장하는 패키징 구조로 점진적으로 이동할 때 주로 사용하도록 의도되었습니다. 완전히 모듈화된 애플리케이션에서 열린 애플리케이션 모듈을 사용하는 것은 대개 최적화되지 않은 모듈화 및 패키징 구조를 암시합니다.

### 명시적 애플리케이션 모듈 의존성 (Explicit Application Module Dependencies)

모듈은 `package-info.java` 파일로 표현되는 패키지에 `@ApplicationModule` 어노테이션을 사용하여 허용된 의존성을 선언하도록 선택할 수 있습니다. 예를 들어 Kotlin은 해당 파일을 지원하지 않으므로, 애플리케이션 모듈의 루트 패키지에 위치한 단일 타입에 어노테이션을 사용할 수도 있습니다.

**Inventory가 모듈 의존성을 명시적으로 설정하는 예시**

* **Java** / **Kotlin**
```java
@org.springframework.modulith.ApplicationModule(
  allowedDependencies = "order"
)package example.inventory;

```



이 경우 `inventory` 모듈 내의 코드는 `order` 모듈의 코드(및 애초에 어떤 모듈에도 할당되지 않은 코드)만 참조할 수 있습니다. 이를 모니터링하는 방법은 애플리케이션 모듈 구조 검증하기(Verifying Application Module Structure)에서 확인하세요.

### 이름 있는 인터페이스 (Named Interfaces)

기본적으로 그리고 고급 애플리케이션 모듈(Advanced Application Modules)에서 설명한 바와 같이, 애플리케이션 모듈의 베이스 패키지가 API 패키지로 간주되므로 다른 모듈로부터의 유입 의존성을 허용하는 유일한 패키지가 됩니다. 만약 다른 모듈에 추가적인 패키지들을 노출하고 싶다면, 이름 있는 인터페이스(named interfaces)를 사용해야 합니다. 해당 패키지들의 `package-info.java` 파일에 `@NamedInterface`를 붙이거나, `@org.springframework.modulith.PackageInfo`가 명시적으로 붙은 타입을 통해 이를 달성할 수 있습니다.

**SPI 이름 있는 인터페이스를 캡슐화하기 위한 패키지 배치**

```text
 Example
╰─  src/main/java
   ├─  example
   │  ╰─  Application.java
   ├─ …
   ├─  example.order
   │  ╰─  OrderManagement.java
   ├─  example.order.spi
   │  ├—  package-info.java
   │  ╰─  SomeSpiInterface.java
   ╰─  example.order.internal
      ╰─  SomethingOrderInternal.java

```

**example.order.spi의 package-info.java**

* **Java** / **Kotlin**
```java
@org.springframework.modulith.NamedInterface("spi")package example.order.spi;

```



이 선언의 효과는 두 가지입니다: 첫째, 다른 애플리케이션 모듈의 코드가 `SomeSpiInterface`를 참조할 수 있게 됩니다. 둘째, 애플리케이션 모듈들은 명시적 의존성 선언에서 이 이름 있는 인터페이스를 참조할 수 있습니다. `inventory` 모듈이 이를 사용한다고 가정하면, 위에서 선언된 이름 있는 인터페이스를 다음과 같이 참조할 수 있습니다:

**전용 이름 있는 인터페이스에 대해 허용된 의존성 정의하기**

* **Java** / **Kotlin**
```java
@org.springframework.modulith.ApplicationModule(
  allowedDependencies = "order :: spi"
)package example.inventory;

```



이중 콜론 `::`을 통해 이름 있는 인터페이스의 이름인 `spi`를 어떻게 연결하는지 확인하세요. 이 설정에서 `inventory` 안의 코드는 `SomeSpiInterface` 및 `order.spi` 인터페이스에 있는 다른 코드에 의존하는 것이 허용되지만, 예를 들어 `OrderManagement`에는 의존할 수 없습니다. 의존성이 명시적으로 기술되지 않은 모듈의 경우, 애플리케이션 모듈 루트 패키지와 SPI 패키지 모두에 접근할 수 있습니다.

만약 애플리케이션 모듈이 명시적으로 선언된 모든 이름 있는 인터페이스를 참조할 수 있도록 표현하고 싶다면, 다음과 같이 별표(`*`)를 사용할 수 있습니다:

**별표를 사용하여 선언된 모든 이름 있는 인터페이스에 대한 허용 의존성 선언하기**

* **Java** / **Kotlin**
```java
@org.springframework.modulith.ApplicationModule(
  allowedDependencies = "order :: *"
)package example.inventory;

```



애플리케이션 모듈의 이름 있는 인터페이스에 대해 더 제너릭한 제어가 필요하다면 커스텀 섹션을 확인하세요.

## 애플리케이션 모듈 배치 커스텀하기 (Customizing the Application Modules Arrangement)

Spring Modulith는 메인 Spring Boot 애플리케이션 클래스에 사용할 `@Modulithic` 어노테이션을 통해 생성하는 애플리케이션 모듈 배치 주변의 일부 핵심 측면들을 설정할 수 있게 해줍니다.

* **Java** / **Kotlin**
```java
package example;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.modulith.Modulithic;

@Modulithic
@SpringBootApplication
class MyApplication {

  public static void main(String... args) {
    SpringApplication.run(MyApplication.class, args);
  }
}

```



이 어노테이션은 커스텀할 수 있는 다음과 같은 속성들을 노출합니다:

| 어노테이션 속성 | 설명 |
| --- | --- |
| `systemName` | 생성된 문서에서 사용할 애플리케이션의 인간이 읽을 수 있는 이름입니다. |
| `sharedModules` | 지정된 이름을 가진 애플리케이션 모듈을 공유 모듈(shared modules)로 선언하며, 이는 해당 모듈들이 애플리케이션 모듈 통합 테스트에 항상 포함됨을 의미합니다. |
| `additionalPackages` | 설정된 패키지들을 추가적인 루트 애플리케이션 패키지로 취급하도록 Spring Modulith에 지시합니다. 다시 말해, 해당 패키지들에 대해서도 애플리케이션 모듈 감지가 트리거됩니다. |

### 모듈 감지 커스텀하기 (Customizing Module Detection)

기본적으로 애플리케이션 모듈은 Spring Boot 애플리케이션 클래스가 위치한 패키지의 직속 하위 패키지에 위치할 것으로 예상됩니다. 대안적인 감지 전략을 활성화하여 Spring Modulith의 `@ApplicationModule` 또는 jMolecules의 `@Module` 어노테이션을 통해 명시적으로 어노테이션이 붙은 패키지만 고려하도록 할 수 있습니다. 이 전략은 `spring.modulith.detection-strategy`를 `explicitly-annotated`로 설정하여 활성화할 수 있습니다:

**애플리케이션 모듈 감지 전략을 어노테이션이 붙은 패키지만 고려하도록 전환하기**

```properties
spring.modulith.detection-strategy=explicitly-annotated

```

기본 애플리케이션 모듈 감지 전략과 수동 어노테이션 전략 중 어느 것도 애플리케이션에 맞지 않는 경우, `ApplicationModuleDetectionStrategy` 인터페이스의 구현체를 제공하여 모듈 감지를 커스텀할 수 있습니다. 이 인터페이스는 단일 메서드 `Stream<JavaPackage> getModuleBasePackages(JavaPackage)`를 노출하며, Spring Boot 애플리케이션 클래스가 위치한 패키지와 함께 호출됩니다. 그런 다음 그 안에 있는 패키지들을 검사하고 명명 규칙 등을 기반으로 애플리케이션 모듈 베이스 패키지로 간주할 패키지들을 선택할 수 있습니다.

예를 들어 커스텀 `ApplicationModuleDetectionStrategy` 구현체를 다음과 같이 선언한다고 가정해 보겠습니다:

**커스텀 ApplicationModuleDetectionStrategy 구현하기**

* **Java** / **Kotlin**
```java
package example;

class CustomApplicationModuleDetectionStrategy implements ApplicationModuleDetectionStrategy {

  @Override
  public Stream<JavaPackage> getModuleBasePackages(JavaPackage basePackage) {
    // 모듈 감지 로직이 여기에 들어갑니다
  }
}

```



이 클래스는 이제 다음과 같이 `spring.modulith.detection-strategy`로 등록될 수 있습니다:

```properties
spring.modulith.detection-strategy=example.CustomApplicationModuleDetectionStrategy

```

만약 모듈의 검증 및 문서화를 커스텀하기 위해 `ApplicationModuleDetectionStrategy` 인터페이스를 구현하는 경우, 해당 커스텀 구현과 등록 설정을 애플리케이션의 테스트 소스(test sources)에 포함시키세요. 그러나 Spring Modulith 런타임 컴포넌트(예: `ApplicationModuleInitializers` 또는 액추에이터 및 관찰성 지원과 같은 프로덕션 준비 기능)를 사용하는 경우에는 컴파일 타임 의존성으로 다음을 명시적으로 선언해야 합니다:

* **Maven** / **Gradle**
```groovy
dependencies {
  implementation 'org.springframework.modulith:spring-modulith-core'
}

```



### 다른 패키지로부터 애플리케이션 모듈 기여받기 (Contributing Application Modules From Other Packages)

`@Modulithic`을 사용하면 어노테이션이 붙은 클래스의 패키지 이외의 패키지에 대해 애플리케이션 모듈 감지를 트리거하도록 `additionalPackages`를 정의할 수 있지만, 이를 사용하려면 해당 패키지들을 사전에 알고 있어야 합니다. 1.3 버전부터 Spring Modulith는 `ApplicationModuleSource` 및 `ApplicationModuleSourceFactory` 추상화를 통해 외부에서 애플리케이션 모듈을 기여하는 것을 지원합니다. 후자의 구현체는 `META-INF`에 위치한 `spring.factories` 파일에 등록할 수 있습니다.

```properties
org.springframework.modulith.core.ApplicationModuleSourceFactory=example.CustomApplicationModuleSourceFactory

```

이러한 팩토리는 `ApplicationModuleDetectionStrategy`가 적용되도록 임의의 패키지 이름을 반환하거나, 모듈을 생성할 패키지를 명시적으로 반환할 수 있습니다.

```java
package example;

public class CustomApplicationModuleSourceFactory implements ApplicationModuleSourceFactory {

  @Override
  public List<String> getRootPackages() {
    return List.of("com.acme.toscan");
  }

  @Override
  public ApplicationModuleDetectionStrategy getApplicationModuleDetectionStrategy() {
    return ApplicationModuleDetectionStrategy.explicitlyAnnotated();
  }

  @Override
  public List<String> getModuleBasePackages() {
    return List.of("com.acme.module");
  }
}

```

위의 예시는 `com.acme.toscan`을 사용하여 그 안에서 명시적으로 선언된 모듈을 감지하고, 또한 `com.acme.module`로부터 애플리케이션 모듈을 생성합니다. 이들로부터 반환된 패키지 이름은 이후 `ApplicationModuleDetectionStrategy`에 노출된 해당하는 `getApplicationModuleSource(…)` 유형들을 통해 `ApplicationModuleSources`로 변환됩니다.

### 이름 있는 인터페이스 감지 커스텀하기 (Customizing Named Interface detection)

애플리케이션 모듈의 이름 있는 인터페이스를 프로그래밍 방식으로 기술하고 싶다면, 여기에 설명된 대로 `ApplicationModuleDetectionStrategy`를 등록하고 `detectNamedInterfaces(JavaPackage, ApplicationModuleInformation)`를 사용하여 커스텀 검색 알고리즘을 구현하세요.

**커스텀 ApplicationModuleDetectionStrategy를 사용하여 이름 있는 인터페이스 감지 커스텀하기**

* **Java** / **Kotlin**
```java
package example;

class CustomApplicationModuleDetectionStrategy implements ApplicationModuleDetectionStrategy {

  @Override
  public Stream<JavaPackage> getModuleBasePackages(JavaPackage basePackage) {
    // 모듈 감지 로직이 여기에 들어갑니다
  }

  @Override
  NamedInterfaces detectNamedInterfaces(JavaPackage basePackage, ApplicationModuleInformation information) {
    return NamedInterfaces.builder()
        .recursive()
        .matching("api")
        .build();
  }
}

```



위에 표시된 `detectNamedInterfaces(…)` 구현에서는 지정된 애플리케이션 모듈의 베이스 패키지 아래에 있는 `api`라는 이름의 모든 패키지에 대해 `NamedInterfaces` 인스턴스를 빌드합니다. Builder API는 패키지를 이름 있는 인터페이스로 선택하거나 거기서 명시적으로 제외하기 위한 추가적인 메서드들을 노출합니다. 빌더는 애플리케이션 모듈에 필수적인 인터페이스이므로, 애플리케이션 모듈의 베이스 패키지에 위치한 모든 public 메서드를 포함하는 이름 없는 명명된 인터페이스(unnamed named interface)를 항상 포함한다는 점에 유의하세요.

`NamedInterfaces`를 더 수동으로 설정해야 하는 경우, 해당 팩토리 메서드들과 `NamedInterface`에 의해 노출된 메서드들을 반드시 확인하시기 바랍니다.
