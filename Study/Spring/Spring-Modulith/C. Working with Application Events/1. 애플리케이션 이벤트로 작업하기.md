# 애플리케이션 이벤트로 작업하기

애플리케이션 모듈을 가능한 한 서로 느슨하게 결합하려면, 모듈 간 상호작용의 주된 방식은 이벤트 발행과 소비가 되어야 해요. 이렇게 하면 이벤트를 발생시킨 모듈이 관심을 가질 수 있는 모든 모듈을 직접 알 필요가 없어져요. 이는 [[D. Integration Testing Application Modules|애플리케이션 모듈 통합 테스트]]를 가능하게 하는 중요한 기반이에요.

흔히 애플리케이션 컴포넌트는 다음과 같이 작성돼요.

애플리케이션 모듈의 다른 Spring Bean을 직접 호출하는 예

- Java

- Kotlin

```java
@Service
@RequiredArgsConstructor
public class OrderManagement {

  private final InventoryManagement inventory;

  @Transactional
  public void complete(Order order) {

    // State transition on the order aggregate go here

    // 주문 애그리거트의 상태 전이가 여기에 들어가요.

    // Invoke related functionality
    // 관련 기능을 직접 호출해요.
    inventory.updateStockFor(order);
  }
}
```

`complete(…)` 메서드는 관련 기능을 끌어당기는 기능적 중력(functional gravity)을 만들어요. 그래서 다른 애플리케이션 모듈에 정의된 Spring Bean과의 상호작용이 이 메서드로 모이게 돼요. 특히 `OrderManagement` 인스턴스를 만들기 위해 의존 대상 Bean 인스턴스까지 준비해야 하므로 컴포넌트 테스트가 더 어려워져요. 이 문제는 [[D. Integration Testing Application Modules|방출 의존성 다루기]]에서도 중요하게 다뤄요. 또한 주문 완료라는 비즈니스 이벤트에 추가 기능을 통합하고 싶을 때마다 이 클래스를 계속 수정해야 해요.

애플리케이션 모듈 간 상호작용을 다음과 같이 바꿀 수 있어요.

Spring의 `ApplicationEventPublisher`로 애플리케이션 이벤트 발행하기

- Java

- Kotlin

```java
@Service
@RequiredArgsConstructor
public class OrderManagement {

  private final ApplicationEventPublisher events;
  private final OrderInternal dependency;

  @Transactional
  public void complete(Order order) {

    // State transition on the order aggregate go here
    // 주문 애그리거트의 상태 전이가 여기에 들어가요.

    events.publishEvent(new OrderCompleted(order.getId()));
  }
}
```

다른 애플리케이션 모듈의 Spring Bean에 의존하는 대신, 기본 애그리거트의 상태 전이를 마친 뒤 Spring의 `ApplicationEventPublisher`를 사용해 도메인 이벤트를 발행해요. 애그리거트 중심의 이벤트 발행 방식을 더 자세히 보려면 [[Spring Data 애플리케이션 이벤트 발행 메커니즘]]을 참고하면 돼요.

이벤트 발행은 기본적으로 동기적으로 일어나므로, 전체 구조의 트랜잭션 의미는 앞의 직접 호출 예제와 같아요. 좋은 점은 단순한 일관성 모델을 얻는다는 거예요. 주문 상태 변경과 재고 업데이트가 모두 성공하거나, 둘 다 실패해요. 나쁜 점은 연결되는 부가 기능이 늘수록 트랜잭션 경계가 넓어지고, 중요하지 않은 부가 기능의 오류 때문에 전체 트랜잭션이 실패할 수도 있다는 점이에요.

다른 접근 방식은 이벤트 소비를 트랜잭션 커밋 시점의 비동기 처리로 옮기고, 보조 기능을 말 그대로 보조 기능으로 취급하는 거예요.

비동기 트랜잭션 이벤트 리스너

- Java

- Kotlin

```java
@Component
class InventoryManagement {

  @Async
  @TransactionalEventListener
  void on(OrderCompleted event) { /* … */ }
}
```

이제 원래 트랜잭션과 리스너 실행이 실질적으로 분리돼요. 원래 비즈니스 트랜잭션이 불필요하게 커지는 것은 막을 수 있지만, 새로운 위험도 생겨요. 어떤 이유로든 리스너가 실패하면 각 리스너가 자체 안전장치를 구현하지 않는 한 이벤트 발행은 사라져요. 더 나쁜 점은 메서드가 호출되기도 전에 시스템이 실패할 수 있으므로, 리스너 내부 안전장치만으로는 완전하지 않다는 거예요.

이 문제를 보완하기 위해 Spring Modulith는 [[3. Event Publication Registry]]를 제공해요.
