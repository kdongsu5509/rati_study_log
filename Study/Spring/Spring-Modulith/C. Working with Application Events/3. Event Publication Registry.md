# Event Publication Registry

Spring Modulith는 Spring Framework의 핵심 이벤트 발행 메커니즘에 연결되는 이벤트 발행 레지스트리를 제공해요. 이벤트가 발행되면, 해당 이벤트를 전달받을 트랜잭션 이벤트 리스너를 찾아요. 그리고 원래 비즈니스 트랜잭션의 일부로 각 리스너에 대한 항목을 이벤트 발행 로그에 기록해요. 그림의 진한 파란색 항목이 그 기록이에요.

기본적으로 `@TransactionalEventListener`가 붙었거나 메타 애노테이션으로 포함한 모든 이벤트 리스너가 대상이에요. 이 동작을 커스터마이즈하려면 Spring Modulith [[Spring Modulith Configuration Properties|설정 프로퍼티]]인 `spring.modulith.events.registry-trigger-annotation`을 확인하면 돼요.

![event publication registry start](https://docs.spring.io/spring-modulith/reference/_images/event-publication-registry-start.png)

Figure 1. 실행 전 트랜잭션 이벤트 리스너 구조

각 트랜잭션 이벤트 리스너는 Aspect로 감싸져요. 리스너 실행이 성공하면 해당 로그 항목을 완료로 표시해요. 리스너가 실패하면 로그 항목은 그대로 남아요. 이렇게 남겨진 항목은 애플리케이션 요구에 맞는 재시도 메커니즘을 붙이는 데 사용할 수 있어요. 애플리케이션 재시작 시 미완료 이벤트를 자동으로 다시 발행하려면 `spring.modulith.events.republish-outstanding-events-on-restart` 속성을 사용할 수 있어요.

![event publication registry end](https://docs.spring.io/spring-modulith/reference/_images/event-publication-registry-end.png)

Figure 2. 실행 후 트랜잭션 이벤트 리스너 구조

## Event Publication Lifecycle (since 2.0)

Spring Modulith 2.0부터 이벤트 발행에는 전용 생명주기가 도입됐어요. 이 생명주기 덕분에 처리 예정, 처리 중, 완료, 실패 상태의 발행을 구분할 수 있어요. 실패한 발행만 다시 제출하거나, 진행 중이던 발행을 실패로 잘못 취급하지 않고 장애에서 복구하기가 쉬워져요.

### Publication states

각 이벤트 발행은 `EventPublication.Status`를 가져요.

|상태|설명|
|---|---|
|`PUBLISHED`|발행이 저장되었고 처리 대기 중이거나 곧 가져갈 상태예요.|
|`PROCESSING`|리스너가 발행을 점유하고 실행 중이에요. 리스너 주변의 인터셉터가 리스너 호출 전에 이 상태로 설정하고, 리스너가 반환되면 `COMPLETED` 또는 `FAILED`로 바꿔요.|
|`COMPLETED`|리스너가 성공적으로 끝났어요. 완료 모드가 `DELETE`가 아니라면 완료 날짜가 설정돼요.|
|`FAILED`|리스너가 예외를 던졌거나, 오래된 발행 자동 실패 처리에 의해 실패로 표시됐어요.|
|`RESUBMITTED`|이전에 실패한 발행이 다시 제출되어 처리 대기 상태가 됐어요.|

![event-publication-lifecycle](https://docs.spring.io/spring-modulith/reference/modulith/_images/event-publication-lifecycle-ab8d6ffd06f5cc626c7bceebcede14fad3d0ccac.svg)

### Publication details

상태 외에도 각 발행은 다음 정보를 추적해요.

|항목|설명|
|---|---|
|마지막 재제출 날짜|발행이 마지막으로 다시 제출된 시각이에요. 재제출된 적이 없다면 값이 없어요. `EventPublication.getLastResubmissionDate()`로 확인할 수 있어요.|
|완료 시도 횟수|리스너가 호출된 횟수예요. 현재 실행도 포함해요. `PROCESSING`으로 이동할 때 증가하므로, 리스너 실행 중 애플리케이션이 중단되어도 시도 횟수는 갱신된 상태로 남아요. `EventPublication.getCompletionAttempts()`로 확인할 수 있어요.|

이 정보로 “실패한 지 X 시간이 지난 발행만 다시 제출하기” 또는 “N회 시도 후 중단하기” 같은 정책을 재제출 API와 옵션으로 구현할 수 있어요.

### Event Publication Staleness and Automatic Marking as Failed

애플리케이션이 중단되거나 리스너가 멈추면 발행이 `PUBLISHED`, `PROCESSING`, `RESUBMITTED` 상태에 계속 머물 수 있어요. 이런 항목을 실패로 취급해 다시 제출하거나 무시할 수 있도록, 각 상태가 어느 정도 오래되면 stale, 즉 오래된 상태로 볼지 설정할 수 있어요. 오래된 발행은 백그라운드 작업에 의해 주기적으로 `FAILED`로 표시돼요.

Spring Modulith는 2.0부터 Staleness Monitor를 제공해요. 이 모니터는 설정 가능한 간격으로 실행되는 스케줄 작업이에요. stale duration 중 하나라도 0이 아닌 값으로 설정되면 모니터가 활성화돼요. 실행될 때마다 `PUBLISHED`, `PROCESSING`, `RESUBMITTED` 상태의 이벤트 발행 중 해당 duration보다 오래된 항목을 찾아 `FAILED`로 표시해요. 이렇게 하면 원래라면 멈춘 채 남아 있을 발행을 `FailedEventPublications.resubmit(…)` 같은 방식으로 복구하거나 별도로 처리할 수 있어요.

커스터마이즈는 `spring.modulith.events.staleness` [[Spring Modulith Configuration Properties|설정 프로퍼티]]로 해요. `published`, `processing`, `resubmitted`가 모두 0이면 기본값 그대로이며, Staleness Monitor는 스케줄 작업을 등록하지 않고 자동 실패 표시도 수행하지 않아요.

### Failed publications and resubmission

레지스트리는 실패한 발행을 명시적으로 다룰 수 있게 해요.

|API|설명|
|---|---|
|`FailedEventPublications` (since 2.0)|이 타입의 Bean을 사용해 실패한 발행만 다시 제출해요. `resubmit(ResubmissionOptions)`를 사용해요.|
|`ResubmissionOptions`|재제출 방식을 제어해요. 배치 크기, 최대 in-flight 수, 발행 최소 경과 시간, 이벤트 타입이나 `completionAttempts` 기준의 선택 필터 등을 설정할 수 있어요. `ResubmissionOptions.defaults()`로 만들고 `withBatchSize(…)`, `withMinAge(…)`, `withFilter(…)` 등으로 커스터마이즈해요.|

재제출하면 상태가 `FAILED`에서 `RESUBMITTED`로 바뀌고 마지막 재제출 날짜가 갱신돼요. 리스너가 실행되기 직전 발행은 `PROCESSING`으로 이동하고 완료 시도 횟수가 증가해요.

실패한 항목뿐 아니라 설정에 따라 오래된 항목까지 포함한 일반적인 미완료 발행에는 기존 `IncompleteEventPublications` API도 계속 적용돼요. 2.0부터는 predicate와 duration 기반 오버로드 외에도 `resubmitIncompletePublications(ResubmissionOptions)`를 지원해요.

## Spring Boot Event Registry Starters

트랜잭션 이벤트 발행 로그를 사용하려면 애플리케이션에 여러 아티팩트 조합을 추가해야 해요. Spring Modulith는 이 작업을 쉽게 하도록, 사용할 영속성 기술을 중심으로 구성된 starter POM을 제공해요. 기본 `EventSerializer` 구현은 Jackson 기반이에요. 사용할 수 있는 starter는 다음과 같아요.

|Persistence Technology|Artifact|Description|
|---|---|---|
|JPA|`spring-modulith-starter-jpa`|JPA를 영속성 기술로 사용해요.|
|JDBC|`spring-modulith-starter-jdbc`|JDBC를 영속성 기술로 사용해요. JPA 기반 애플리케이션에서도 동작하지만, 실제 이벤트 영속성에는 JPA provider를 우회해요.|
|MongoDB|`spring-modulith-starter-mongodb`|MongoDB를 영속성 기술로 사용해요. MongoDB 트랜잭션도 활성화하므로 서버는 replica set 구성이 필요해요. `spring.modulith.events.mongodb.transaction-management.enabled` 속성을 `false`로 설정해 트랜잭션 자동 구성을 비활성화할 수 있어요.|
|Neo4j|`spring-modulith-starter-neo4j`|Spring Data Neo4j 뒤에서 Neo4j를 사용해요.|

## Managing Event Publications

애플리케이션 실행 중 이벤트 발행은 다양한 방식으로 관리해야 할 수 있어요. 미완료 발행은 일정 시간이 지난 뒤 해당 리스너에 다시 제출해야 할 수 있어요. 반대로 완료된 발행은 데이터베이스에서 제거하거나 아카이브 저장소로 옮겨야 할 가능성이 커요.

이런 housekeeping 요구는 애플리케이션마다 크게 다르기 때문에, Spring Modulith는 두 종류의 발행을 모두 다룰 수 있는 API를 제공해요. 이 API는 애플리케이션에 추가할 수 있는 `spring-modulith-events-api` 아티팩트로 제공돼요.

Spring Modulith Events API 아티팩트 사용하기

- Maven

- Gradle

```none
dependencies {
  implementation 'org.springframework.modulith:spring-modulith-events-api:2.1.0'
}
```

이 아티팩트에는 애플리케이션 코드에서 Spring Bean으로 사용할 수 있는 주요 추상화가 들어 있어요.

|추상화|설명|
|---|---|
|`CompletedEventPublications`|완료된 모든 이벤트 발행에 접근하고, 전체 또는 특정 기간보다 오래된 완료 발행을 즉시 제거하는 API를 제공해요. 예를 들어 1분보다 오래된 완료 발행을 제거할 수 있어요.|
|`IncompleteEventPublications`|모든 미완료 이벤트 발행에 접근해 다시 제출할 수 있어요. 특정 predicate에 맞는 항목, 원래 발행일 기준 특정 `Duration`보다 오래된 항목, 또는 `ResubmissionOptions` 기반의 커스텀 조건에 맞는 항목을 다시 제출할 수 있어요. `ResubmissionOptions` 방식은 2.0부터 지원돼요.|
|`FailedEventPublications` (since 2.0)|위의 실패 발행과 재제출 설명처럼, 실패한 이벤트 발행만 `resubmit(ResubmissionOptions)`로 다시 제출할 수 있어요.|

## Event Publication Completion

트랜잭션 이벤트 리스너나 `@ApplicationModuleListener` 실행이 성공적으로 끝나면 이벤트 발행은 완료로 표시돼요. 기본적으로 완료 처리는 `EventPublication`에 완료 날짜를 설정하는 방식으로 등록돼요. 즉 완료된 발행도 Event Publication Registry에 남아 있고, 위에서 설명한 `CompletedEventPublications` 인터페이스를 통해 조회할 수 있어요.

이 방식의 결과로, 오래된 완료 `EventPublication`을 주기적으로 삭제하는 코드를 따로 마련해야 해요. 그렇지 않으면 관계형 데이터베이스 테이블 같은 영속성 추상화가 끝없이 커지고, 새로운 `EventPublication`을 만들고 완료 처리하는 저장소 상호작용이 느려질 수 있어요.

Spring Modulith 1.3은 `spring.modulith.events.completion-mode` 설정 속성을 도입해 두 가지 추가 완료 모드를 지원해요. 기본값은 `UPDATE`이고, 앞에서 설명한 완료 날짜 갱신 전략이에요.

대안으로 완료 모드를 `DELETE`로 설정할 수 있어요. 이 경우 레지스트리의 영속성 메커니즘은 완료 시 `EventPublication`을 삭제해요. 그러면 `CompletedEventPublications`는 더 이상 어떤 발행도 반환하지 않지만, 완료 이벤트를 저장소에서 직접 정리할 필요도 없어져요.

세 번째 옵션은 `ARCHIVE` 모드예요. 이 모드는 항목을 아카이브 테이블, 컬렉션, 노드로 복사해요. 아카이브 항목에는 완료 날짜가 설정되고 원본 항목은 제거돼요. `DELETE` 모드와 달리, 완료된 이벤트 발행은 이후에도 `CompletedEventPublications` 추상화를 통해 접근할 수 있어요.

## Event Publication Repositories

이벤트 발행 로그를 실제로 쓰기 위해 Spring Modulith는 `EventPublicationRepository` SPI와 JPA, JDBC, MongoDB 같은 트랜잭션 지원 영속성 기술용 구현을 제공해요. 사용할 영속성 기술은 Spring Modulith 애플리케이션에 해당 JAR를 추가해 선택해요. 이 작업을 쉽게 하도록 전용 starter도 준비되어 있어요.

JDBC 기반 구현은 해당 설정 속성인 `spring.modulith.events.jdbc.schema-initialization.enabled`가 `false`로 설정되어 있지 않으면 이벤트 발행 로그용 전용 테이블을 만들어요. 필요한 테이블이 이미 있으면 스키마 생성은 당연히 물러나요. 예를 들어 Flyway나 Liquibase 같은 데이터베이스 마이그레이션 도구로 테이블을 이미 만든 경우가 그래요. 자세한 내용은 Spring Modulith 부록의 [[Spring Modulith Schemas|schema overview]]를 참고하면 돼요.

## Event Serializer

각 로그 항목에는 원래 이벤트가 직렬화된 형태로 들어 있어요. `spring-modulith-events-core`에 포함된 `EventSerializer` 추상화는 이벤트 인스턴스를 데이터 저장소에 적합한 형식으로 바꾸는 여러 전략을 꽂을 수 있게 해요.

Spring Modulith는 `spring-modulith-events-jackson` 아티팩트를 통해 Jackson 기반 JSON 구현을 제공해요. 이 아티팩트는 기본적으로 표준 Spring Boot 자동 구성을 통해 `ObjectMapper`를 사용하는 `JacksonEventSerializer`를 등록해요.

## Customizing the Event Publication Date

기본적으로 Event Publication Registry는 이벤트 발행 날짜로 `Clock.systemUTC()`가 반환하는 날짜를 사용해요. 이 값을 커스터마이즈하려면 애플리케이션 컨텍스트에 `Clock` 타입 Bean을 등록하면 돼요.

```java
@Configuration
class MyConfiguration {

  @Bean
  Clock myCustomClock() {
    return … // Your custom Clock instance created here.
  }
}
```

테스트나 재현 가능한 시간 정책이 필요한 경우, 이 방식으로 발행 시각을 통제할 수 있어요.
